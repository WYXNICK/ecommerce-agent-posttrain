# 4×4 终局奖励 GRPO（R-batch）

**状态：训练与开发集选模已完成。** 见[结果](results.md)。 从修复 SFT step72 重新初始化 RL adapter 与优化器；原终局 step500 继续作为当前主结果。本轮不预设提升，不自动运行 test1000。

## 设计依据

原终局配方每次更新只有 2 个有效任务，500 步接受 4,000 条轨迹；采样日志共生成 3,252 个组，其中 2,037 个等分组（62.6%）被过滤。需要区分组内缺少差异与每次更新任务覆盖少：动态采样已解决前者，本轮优先检验扩大任务覆盖、降低组间梯度波动的收益。

S0 起点消融未显示更好的开发集绝对表现，故继续使用修复 SFT。此前 8×4＋KL＋250 步同时改变多个因素，开发集最好 227/300，未超过原终局 228/300；这不能单独证明大 batch 无效。本轮采用较温和的 **4×4，无额外 KL，500 步**，不叠加奖励、学习率或温度改动。

这是一版基于现有证据的优先配置，不是已经证实的全局最优。每题从4条增至8条可能提高组内探索，但会减少同预算任务覆盖，因此本轮不同时改变。

## 冻结配方

| 项目 | 设置 |
|---|---|
| 起点 | S-repair step72，与原终局完全相同；SHA256 由原配置固定 |
| 有效 batch | **4 个不同任务 × 每题 4 条 = 16 条/更新** |
| 采样 | 每波 2×4、并发 8；最多16波补采，凑齐4个有效组才更新 |
| 更新预算 | 500 次；接收8,000条轨迹；250步接收4,000条作为等轨迹预算对照 |
| 奖励与优势 | 原 Reward v3；非终局模型失败−0.65；基础设施/不可验证过滤整组；组内均值中心化，不除标准差 |
| 优化 | LR1e−6、预热15步、clip0.2、梯度裁剪1.0、LoRA r16/alpha32、KL=0 |
| 探索 | temperature=1、top_p=1、seed=42 |
| 保存与选模 | 每50步保存＋完整dev300；含SFT起点，成功数→Reward→较少动作→较早步数 |
| 停止 | 完整500次有效更新；数值/服务异常或连续10次有界补采失败停止，不按一次dev波动提前停止 |

## 实现与验收

复用原训练器，以 [独立配置覆盖](../../configs/grpo_batch.json) 调整 batch 和补采上限。采样期间策略固定；模型仅针对动作token训练，按全局动作token数归一化、双卡梯度求和。分波采样和逐动作梯度累积扩大有效batch，不增加同时驻留的序列数。

保留已验证的 FLA、FlashAttention、动作长度负载均衡和 vLLM 8路并发，不引入异步过期策略或多轮重复更新。**18项必要 CPU 验收已通过**，覆盖配置隔离、起点一致、组完整性、过滤和并发上限、未凑齐不得更新、两卡梯度归一化；正式首步沿用logprob一致性、裁剪比例和有限梯度检查。

## 结果与证据

- 比较原终局500步、此版250步（相同接收轨迹数但更新次数不同）、此版500步；按规则报告开发集选中模型。记录实际生成量、接收量、token和耗时，不能把双倍预算的收益全部归因于batch。
- 既有test结果仅保留对照，本轮不读取测试失败轨迹、不据此调参。若后续评测，需要先固定候选；重复使用同一测试集也不能替代独立留出与多种子验证。
- `outputs/grpo/batch/`：进度、训练/采样日志、逐条轨迹、dev原始结果、GPU监控和TensorBoard；`results/grpo/batch/`：完成后的模型身份、结果和归档清单。
- 每50步检查点和阶段证据先保存开发机 `/tmp` 并校验，再异步归档已可用HDFS。新备用HDFS仍受访问控制限制，不使用旧回执冒充新目录备份。
- 独立后台监督器正常或可捕获异常退出后恢复双卡保活；Worker被平台强制销毁时，任何机内脚本均无法恢复该Worker。

### 执行效率核验

**结论：保留正式训练实现。** 在独立双 H100 上，使用已保存的非零 RL adapter、优化器和真实训练轨迹重放更新；任务、优势、动作损失及全局 token 归一化不变。GPU0 预留20 GiB模拟推理服务，两卡各保留15%安全余量，计时不混入保活负载。

| 执行方式 | 同一批完整更新耗时 | 结论 |
|---|---:|---|
| 原实现 | 首次148.56秒，重复99.45秒 | 以预热后的结果比较，避免夸大收益 |
| 关闭全部／一半激活重算 | 未完成 | 2.2万token长序列超过安全显存预算 |
| 两条微批＋补齐掩码 | 245.71秒 | 更慢，不采用 |
| 两条微批＋因果右补齐 | 首次117.48秒，重复93.13秒 | 更新耗时仅减少6.4%，不采用 |

结合正式训练采样/更新约91/129秒的耗时占比，最佳方案仅对应**约3.7%的整步耗时降低估计**，未达到预先设置的1.3倍整体提速目标；不是实测端到端收益。最优微批与原实现相比，梯度相对L2差异约11.3%、单步参数更新约2.12%，高于原实现重复测量的1.07%和0.19%。损失接近不能证明最终效果不变，也不据此断言一定退化。

验证代码见 [benchmark_update.py](../../scripts/grpo/benchmark_update.py)，方法参数、完整测量和局限见 [核验结果](../../results/grpo/batch-performance/summary.json)。仅保留独立测试工具与证据，未修改正式训练器、运行环境或当前训练配方。
