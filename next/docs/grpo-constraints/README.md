# 基于证据的约束型终局奖励 GRPO

**状态：运行中。** 原终局GRPO step500仍为正式主结果。本阶段验证奖励语义修正，不能预先宣称训练提升或理论最优。

## 1. 为什么修改

Reward v3把品类、预算作为硬约束，却把规格、品牌、型号和功能放入加权匹配。明确要求的规格错误可能被其他维度的匹配抵消。实际训练任务15098要求“驱动板保护壳”，模型选择“支架”，得到0.04375；另外三条循环失败为−0.65，该错误购买因此获得约+0.5203的优势。

原终局GRPO的test1000成功数766→778，但循环52→24、错误购买12→26。它有实际收益，也存在行为取舍，不能单凭这些结果认定reward hacking。本版只用冻结训练轨迹审计规则，不把测试失败题回流训练。

**设计原则：必选条件不可被其他得分补偿；只对证据充分的违反重罚，偏好匹配继续提供渐进信号。** 新贡献是修正奖励语义，并接通训练资格和组内优势，而不是重做已有的失败分类或调一个奖励系数。

## 2. 约束与证据

复用冻结任务标注和环境比较器，不引入新的LLM裁判、检索服务或自然语言解析器。

| 条件 | 足够的证据 | 处理 |
|---|---|---|
| 品类、预算 | 原Reward v3硬约束 | 保持原错误购买评分 |
| 明确品牌、型号 | `feature_sources`为显式品牌／型号要求；要求值在任务契约中；对应比较器返回可验证的`fail`，实际字段非空 | 必选约束违反 |
| 规格选错或漏选 | 来源为`instruction.instruction_options`；规格轴可解析；比较器给出`wrong_values` | 必选约束违反 |
| 商品不提供必选规格 | 同一明确规格来源；规格轴可解析；比较器给出`unavailable_values` | 不符合要求的商品选择 |
| 明确功能反证 | 属性要求在指令中出现，比较器给出`negated`反证 | 必选约束违反 |
| 缺少功能关键词、风格等匹配项 | 只有`missing`，不能证明商品不支持 | 保留原部分匹配评分 |
| 规格轴歧义、来源不明、无法判断 | 没有足够的确定性证据 | 沿用原评分／过滤规则 |

“明确要求”以冻结任务标注及来源为准，不声称解决开放式语言中所有偏好、否定和跨商品规格同义表达。品牌／型号沿用原比较器；标注或比较器本身的错误仍是本方案的边界。

## 3. 奖励与训练资格

按顺序执行，不叠加混合权重、成功奖金或动作奖励：

1. **基础设施失败：** 继续过滤，不根据局部证据恢复。
2. **真实完整的购买终局存在已确认的必选条件违反：** 使用现有`wrong_purchase`训练奖励 **−0.85**；多项违反不重复扣分。
3. **其余结果：** 保持原训练奖励及资格。严格成功仍为1、合格替代购买0.55、模型非终局失败−0.65。

如果环境因价格等证据不足返回`reward_unverifiable`，但独立证据已确认必选规格等条件违反，该购买仍不能满足全部要求，可以恢复为负向训练样本。只有价格未知而没有确认的违反时，继续过滤。

**不改写原始`final_reward`、`reward_detail`、`reward_valid`、`failure_kind`。** 另存`original_training_reward`、新`training_reward`和带来源的约束判定。恢复训练资格不等于恢复评测成功；正式评测仍使用原Reward v3及完整严格成功定义。

惩罚值直接读取冻结环境配置，避免重复维护奖励常数。实现：[constraint_reward.py](../../scripts/grpo/constraint_reward.py)。

## 4. GRPO接入与运行

- 同一修复SFT step72、同一2000题GRPO池；2题×4条、500次有效更新；LR1e−6、无额外KL、原LoRA与双卡计算实现均沿用。
- **先计算新奖励，再筛组，再计算组内均值优势。** 过滤未解决异常组、等分组；最多8波补采，连续10轮无有效批次则停止。
- 每50步保存、dev300评测和归档；起点参与选模。禁止从旧奖励配方检查点跨版本续训。
- 复用后台监督、开发机确认备份、异步HDFS归档及结束／可捕获异常后的双卡保活。
- 中断后用`--resume "$CHECKPOINT"`接续原输出目录：核对训练契约与最后更新，恢复优化器、随机状态和任务流；先补齐该检查点未完成的开发集评测，再继续更新。原日志与运行清单保留，续训源码另存快照，评测曲线和归档沿用同一入口。
- 日志与TensorBoard分别记录新奖励、原有效训练奖励及其分母、原环境奖励、惩罚／恢复计数、进入更新的违约样本及其正优势数。
- dev分数保持不变，单列`constraints.json`及看板计数；同时观察违约、循环和原成功保留，不用诊断分替换选模口径。

配置：[grpo_constraints.json](../../configs/grpo_constraints.json)。使用原入口：

```bash
next/scripts/grpo/launch.sh --variant constraints \
  --model "$S_REPAIR_MODEL" --work "$GRPO_WORK" --output "$GRPO_OUTPUT"
```

输出独立使用`outputs/grpo/constraints/`，沿用`SHOP_RUNTIME`、内核及归档队列环境变量；路径通过参数传入，不写入源码。

## 6. 如何判断有效

规则正确、训练与筛组一致只是必要条件。最终必须看到严格成功及原成功保持改善、违约购买下降，且不能以更多循环或放弃换取表面改善。dev固定候选后再决定是否测试；报告原Reward v3、逐题得失和采样成本，未证明优于原结果前不替换主结果。

本版是**要求语义→可验证约束→奖励与样本资格→组内优势→固定评测**的一致性修正，不是新GRPO算法，也不保证单种子训练显著提升。
