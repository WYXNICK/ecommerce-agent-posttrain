## 2. 固定模型、数据与评测口径

### 模型

| 角色 | 当前选择 | 使用边界 |
|---|---|---|
| 正式教师 | **gpt-6-astra-2026-09-03，high 推理** | 使用已验收的冷启动和修复成品；不需要重复采集已有数据 |
| 独立参考教师 | gpt-6.1-sol-2026-09-29 | 数据及结果独立保留，不混入主线 |
| 主实验学生 | **Qwen/Qwen3.5-2B** | 固定 revision、模板与预算，先完成双 H100 主线 |
| 可选扩展 | Qwen/Qwen3.5-4B | 主线完成后再验证迁移，不是当前必做项 |

原始学生本身是已后训练模型；本项目的 Baseline 指**领域训练前的起点**。教师通过共享执行器进行真实交互，不依赖 logits 或私有推理文本。模型及数据身份以[执行清单](../configs/execution_manifest.json)、[主数据选择](../configs/data_selection.json)为准。

教师正式 test1000：Sol **80.4%**，Astra **80.9%**，不能凭 0.5 个百分点断言明显优劣。Astra 是已固定的主线选择；教师成绩不是学生的理论上限。

### 数据规模

| 用途 | 当前数量 | 使用方式 |
|---|---:|---|
| 教师候选任务 | 4,000 | 冷启动示范采集及训练池失败挖掘 |
| GRPO 任务池 | 2,000 | 独立的在线 RL 候选任务 |
| SFT 验证采集候选 | 800 | 生成独立成功验证轨迹，不参与训练 |
| 冷启动成品 | **2,000 条训练＋200 条验证** | 已完成；验证仅看 loss |
| 开发集 | **300 题** | 选模、调参、失败诊断；50 题子集仅用于必要的开发检查 |
| 锁定测试集 | **1,000 题** | 最终比较，不用于选模、调参或数据回流 |
| 训练备用任务 | 3,977 | 普通示范采集及必要扩量，具体已用 ID 见清单 |
| 修复与普通成品 | **各 144 条** | 每组再混入相同的 144 条原示范，共 288 条训练数据 |

数量区分“候选任务”与“验收后的轨迹”，不相加冒充训练规模。训练、验证、开发、测试按任务与近重复组隔离；环境数据和任务来源见[数据准备总结](data-preparation/README.md)。

### 统一评测

- 固定 ShopSimulator Environment v2.1、Reward v3、observation v2、tool schema v2，以及共享守卫、终止规则与 token 预算。
- 严格成功要求完整 `gold_purchase` 且 `reward_valid=true`。模型失败保留在分母；基础设施问题单独识别和处理。
- 主指标为严格成功率；同时报告 Reward v3、错误购买、循环、步数、token 和计算成本。
- 开发集成绩用于选模，不能代替测试集泛化成绩。最终使用逐题配对差异与区间；相关任务按组处理，不保证小幅提升显著。
- 人工分层抽查约 100 条开发轨迹，核对成功、失败和争议案例。API 复核需引用执行证据；Rubric/过程分不替代环境严格成功。

### 补充挑战评测：Hard Set

保留 test1000 主结果，另从与参评模型训练隔离的备用任务中准备复杂购物挑战集；不按模型输赢挑题。已完成[标准与候选审计](hard-evaluation/README.md)：普通增量 SFT 不参评，其独立使用的 179 题恢复资格；3,977 道待筛题中，117 道命中至少两类难点，文本初审后保留 **105 道待验收候选**。这套集合不用于普通增量 SFT 及其派生模型的无泄漏比较。后续先完成语义与可执行路径验收、冻结名单并加入训练留出保护，再统一比较已选模型；当前未启动 Hard 评测，不为凑 300 题降低门槛。

## 3. 已完成：冷启动与一轮数据回流

### 冷启动 SFT（已完成）

从固定原始 2B 开始，使用 Astra 2,000 条示范，双 H100、BF16 LoRA、3 epoch、有效批次 8、LR 1e-4。只监督 assistant 动作，环境观察不参与 loss；完整长轨迹不静默截断。

第 250 / 500 / 750 步分别完成 dev300：**202 / 208 / 220 题成功**，按预先固定规则选中 step 750。训练配方、验证 loss 与证据见 [SFT 总结](sft/README.md)和[结果](sft/results.md)。

### 失败回流与普通增量对照（已完成）

**问题：定向修复是否比增加普通成功示范更有效？**

- 已完成失败挖掘、真实前缀回放、Astra 接管与严格成功验收，冻结修复示范 **144 条**；普通示范同为 **144 条**，领域计数匹配。采集目标原为 300 条，候选耗尽后按预设最低 100 条门槛使用实际成品。
- 本轮直接复用冻结成品，不重复调用教师。采集源模型与哈希保留在数据清单中；这些数据不能描述为当前 S0 新生成的在线失败。
- 两组都从**当前选中的同一个 S0**独立初始化 LoRA，加入相同 144 条原示范；每组 **2 epoch、72 次更新、LR 2e-5**。修复组只监督教师续写的后缀。
- 每组第 36 / 72 步在完整 dev300 评测。按严格成功数、平均奖励、较少动作、较早检查点选择；再与 S0 比较，完全同分时保留 S0。
- 两组匹配教师、领域计数、样本数、回放数据与更新预算；**监督 token、任务难度和 GPU 时间并不完全相同**，需如实报告。

**本轮结果：** S0 220/300、普通增量组 218/300、修复组 226/300；修复组相对 S0 提升 2.00 个百分点，相对普通组提升 2.67 个百分点。错误购买减少，但循环和平均步数增加；这是单种子、开发集选模结果，稳定收益仍待独立测试与多种子验证。

验收重点：回放一致、学生失败前缀不被监督、对照起点一致、数据无泄漏、原始证据完整。此对照检验整套修复策略，不单独证明某一组件的因果收益。无收益时允许保留 S0 进入 GRPO；不自动增加第二轮。

详见[阶段方法](data-reflow/README.md)、[配方](../configs/reflow.json)和[冻结数据清单](../data/reflow/r1/manifest.json)。

## 4. GRPO 主方案与待执行对照

### 已有主结果：R-outcome

S-repair step72 → 终局奖励 GRPO：2个有效任务×每题4条，500次更新；每50步保存及dev300选模，起点也参与。Reward v3、模型失败保留、基础设施/不可验证过滤、组内均值优势、无额外KL/长度奖励均已固定。结果与完整训练证据保留，见[方法](grpo/README.md)、[测试对照](evaluation/results.md)。

### 已完成：R-s0（起点消融）

- **只改起点：** 使用已选定且已评测的S0 step750，不经过修复SFT；重新初始化RL LoRA和优化器。其余完整沿用R-outcome配方：2×4、500次有效更新、LR1e−6、temperature/top_p=1/1、KL=0、每50步保存和dev300评测。
- **复用：** 教师成品、S0模型、2000题GRPO池、环境与评测协议、训练执行器和备份机制；不重新采教师、不重跑SFT。必要验收通过后直接正式运行。
- **比较：** 分别报告相对各自SFT起点的增益，以及两个RL模型的最终绝对表现。S0→已有主结果的总提升不能全部记为GRPO收益；同种子对照也不能证明多种子稳定性。
- **停止与保存：** 完整500次有效更新；每50步选模，不按短期波动提前停止。沿用数值异常、服务退出和有界补采失败停止。检查点、训练/评测日志、逐题轨迹、模型身份先备份开发机，再异步归档HDFS；结束或可捕获失败后恢复双卡保活。
- **结果隔离：** `docs/grpo-s0/`、`results/grpo/s0/`、`outputs/grpo/s0/`独立保留，不覆盖R-outcome。入口与当前状态见[阶段说明](grpo-s0/README.md)。本轮自动执行dev300，不自动追加test1000。

### 当前运行：R-batch（4×4终局GRPO）

修复SFT step72起点，**4个有效任务×每题4条、500次更新**；每波2×4、并发8、最多16波补采。原奖励、LR1e−6、温度1、KL=0及每50步保存/dev300选模保持不变。详见[方案与状态](grpo-batch/README.md)。

第250步对应原版4000条接收轨迹，第500步为8000条；分别报告预算及实际生成token/GPU时间，不能把更多数据的收益全归因于batch。完整训练结束或真实运行异常时停止，不按短期dev波动提前结束；只自动运行dev300，test1000不在本轮执行范围。

任务池、教师与SFT成品全部复用；四个原GRPO候选继续保留。本轮不依据已有测试失败题定向训练，后续配置与候选仍通过dev固定。更强泛化结论需要独立留出与多种子验证。

## 5. 复用、执行与交付

| 模块 | 已具备 | 后续核心工作 |
|---|---|---|
| 数据与采集 | 冻结划分、教师真实交互、验收、usage、前缀回放与后缀监督 | 使用既有成品；补齐实际计费口径与必要人工复核 |
| SFT | 冷启动及普通/修复增量对照均完成，已选定 RL 起点 | 复用选中模型；稳定性主张需后续验证 |
| 评测 | 共享协议、逐题轨迹、严格成功、模型与数据哈希 | 跨组配对统计、多种子、最终测试与失败分析 |
| GRPO | 原终局step500为主结果；S0对照已完成；局部信用和稳定终局为探索备份 | 运行4×4 batch对照，开发集固定候选后评测 |
| 工程 | 后台执行、监控、检查点同步、HDFS 备份、退出保活 | 保持训练与结果身份一致，阶段完成即整理同步 |

- **资源：** 当前使用两张 H100 80GB。GRPO 的长轨迹、并发和分支预算以实际显存与吞吐验收为准，双卡不能简单视作一块 160GB；不承诺固定完成时间。
- **保存：** 检查点与导出模型先校验备份到开发机 `/tmp`，HDFS 可写时自动同步；不能只存在 worker。保留关键训练/评测日志、TensorBoard、逐题轨迹、配置、源码与模型哈希，整理清理前验证备份。
- **运行：** 后台独立会话执行，结束或可捕获异常后恢复双卡保活。保活负载不计作训练吞吐；worker 被回收不能靠进程脚本恢复。
- **文档：** 阶段完成后及时更新本表、`docs/<阶段>/` 总结与 `results/<阶段>/` 清单并推送当前分支。总结只写目的、方法、结果与局限；实时步数、排错记录和详细日志保留在 `outputs/`。
- **最终交付：** 冻结候选后完成 test1000 对照，输出统一结果表、改善与退化案例、训练/推理成本及可复现入口。允许最好的 SFT 成为交付模型，不为证明 GRPO 有效而挑选结果。

项目面试主线是：**数据如何变好、训练信号为何有效、结果如何被验证**。只报告已完成且有证据的贡献，不扩展浏览器、多 Agent 或新训练框架来堆功能。
