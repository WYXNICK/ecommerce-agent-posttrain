# 新版实现边界

继承仓库根目录 `AGENTS.md` 的运行契约与开发原则。

- 本轮及后续完善版本的代码、配置、数据、测试和结果说明放在 `next/`。
- 外层开源代码、原有数据与历史实验保留作参考，不为新版适配而修改。
- 复用某个模块并需要修改时，先复制到 `next/`，再调整实现、导入和配置；未复制的外层实现仅可只读调用。
- 商品库、搜索索引、模型等大文件可只读复用或使用外部存储，不为目录隔离重复存放；在新版配置及清单中记录来源和校验信息。
- 新训练除隔离外层 `data/evaluation/tasks.jsonl` 外，还须保护本目录冻结的验证、开发、测试任务及重复组，按 `docs/data-preparation/methodology.md` 使用留出清单。测试不得用于选模、修复回流或调参。
- 新版结果单独报告；外层 SFT/E1/E2/E3 属于历史参考，不能混入新版实验表冒充同协议对照。
- 正式教师固定为 GPT-6 Astra，冷启动训练/验证数据以 `configs/data_selection.json` 指向的主成品清单为准；后续教师修复沿用同一冻结快照。GPT-6.1-Sol 的数据、轨迹及结果保持原样，仅作独立参考，不默认混合或替换主线。
- 每个正式任务须有简明的执行与结果说明，记录方法、冻结配置、完成状态、关键指标及证据路径；运行中明确标注未完成，结束后更新。只保留复盘必要信息，不逐项堆砌探查过程。

## 阶段交付与 GitHub 同步

- 每完成一个阶段或独立子阶段，整理该阶段代码、必要配置、验收结果和成品，在当前完善分支提交并推送 GitHub。已完成部分可以先交付；仍在运行的探索明确标注未完成，不混作正式结果。
- 整体设计的唯一入口为 `docs/project-completion-plan.md`；全局文档放 `docs/` 顶层，每个阶段在 `docs/<阶段>/` 建独立目录，以 `README.md` 汇总目的、实现方案、结果、验收与局限、后续如何复用，相关详细说明放同阶段目录。
- 阶段总结服务于复盘和面试准备，不写成执行流水账；源码指纹、原始计数和成品哈希按阶段及模型放 `results/<阶段>/<模型>/`，已冻结的数据成品放 `data/`。新运行输出按阶段及模型放 `outputs/<阶段>/<模型>/`，采集与评测分开，不移动活动进程的原始证据。
- 自动运行报告、重试/探查记录和完整日志保留在本地 `outputs/` 或明确标注的本地运行报告中，不混入阶段总结或作为大量中间文档提交。原有外层文档和历史成果继续保留。
- 推送前核对提交范围、密钥、数据隔离及相关检查；凭证、运行环境、缓存、模型权重和冗长日志不提交 Git。完成后报告分支、提交和关键总结入口。

## 开发原则

后续修改代码或新增实现时，必须遵循以下原则：

- **简单且正确。** 尽量少的代码和组成部分，同时保持清晰可读。
- **只处理真实可能发生的失败。** 外部输入在边界校验；内部信任已建立的契约，不为不可能状态堆防御分支、兜底和恢复逻辑。
- **小而内聚的函数。** 职责、输入输出、依赖明确；按职责拆分，不为缩短行数机械拆函数。
- **偏好纯函数和不可变数据。** 副作用集中在明确边界，依赖显式传入，避免隐藏修改和共享可变状态。
- **重复或结构不合适时先重构。** 减少特殊分支、包装层和补丁；抽象围绕真实领域概念或已存在的共性，不预建通用框架。
- **每个事实只保留一个权威来源。** 能从规范状态推导的数据，就不再维护一份需要同步的状态。
- **防御要适当，避免过度防御逻辑。** 对非实际可能发生的场景，不单独添加防御逻辑。
